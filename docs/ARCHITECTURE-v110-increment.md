## 1. 需求与范围

用户原话：

1. 「你能找到完整的保单托管报告吗？参考大童保险经纪、明亚、黎明等保单托管模板，
   在我们的软件里增加保单托管功能？」
2. 「这个报告要动态自动生成，我的保单会新增、过期或者其他变化。」

### 1.1 三次拍板（AskUserQuestion）

| 问题 | 选择 |
|---|---|
| 报告形态 | **页面内查看为主**，可手动导出 Word / PDF |
| 缺口分析 | **填 3 个参数算额度缺口**（家庭年收入 / 负债余额 / 年生活支出） |
| 篇幅 | **完整版 10–12 页** |
| 责任表 | **纳入，手动录入 + 按险种模板** |
| 入口 | **独立页面 + 顶栏 tab** |

### 1.2 明确不做

- **条款 PDF 自动拆解**：没有条款库、不联外部模型，正则抽取「100%」「60%」的准确率
  撑不起理赔判断，错一个数比不填更糟；
- **公司介绍 / 经纪人介绍**：中介的销售物料，与工具无关；
- **现金价值 / 生存金 / 分红 / 绿通权益**：库里没有这些数据，不编；
- **生成后存档的报告快照**：见 §2。

## 2. 核心约束：报告必须是「现算」的

用户明确说「我的保单会新增、过期或者其他变化」。这条直接否掉了最常见的实现方式
（生成一次、存进 `reports` 表、页面读存档）：

| 方案 | 问题 |
|---|---|
| 生成快照存表 | 保单改了要手动「重新生成」，忘了就是错的；还要处理快照版本、清理策略 |
| 定时任务刷新 | 用户点开时看到的仍可能是几小时前的数；定时器还要处理停机补跑 |
| **每次请求现算（采用）** | 一次 SQL 全表扫 + 纯内存聚合，家用数据量（几十张单）耗时可忽略 |

实现上的三条配套：

1. `build_report()` **纯读**，不写库、不缓存；
2. 所有派生量走 `calc.calc_schedule()`，与看板同源，不另造日历算术；
3. `meta.dataUpdatedAt` = 保单 / 责任 / 成员三表 `max(updated_at)`，
   前端据此提示「数据变了，点重新生成」。

前端对应：`#/report` 每次进入都请求，页面不写 `store` 缓存；刷新按钮直接重新拉接口。

## 3. 数据模型：PolicyCoverage

### 3.1 为什么需要它

一张保单的「保额」经常不是一个数字：重疾赔 100%、中症 60% 赔 2 次、轻症 30% 赔 3 次、
身故另算。只留一个 `insured_amount`，缺口分析只能瞎猜。

### 3.2 表结构（新表，`create_all` 自动建，**零迁移**）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | VARCHAR(36) | `cv_` + 12 hex |
| `policy_id` | FK → policies.id | `ON DELETE CASCADE` |
| `category` | VARCHAR(12) | 中文枚举，9 类（重疾/中症/轻症/身故全残/医疗/意外/年金/保费豁免/其他） |
| `name` | VARCHAR(40) | 条款里的责任名 |
| `amount` | Money（整数分） | 固定金额；与 `ratio` 二选一或并存，`amount` 优先 |
| `ratio` | INT | 赔付比例（%），0–500 |
| `times` | INT | 赔付次数，1–99，为空 = 不限 |
| `deductible` | Money | 免赔额，只对医疗有意义 |
| `note` | VARCHAR(120) | 备注 |
| `sort_order` | INT | 录入顺序 |

**新表不登记 `_ADDITIVE_COLUMNS`**：`Base.metadata.create_all` 会建它，
老库升级时自动补建（已用「旧库 + 删表 + 重启」验证，见 `docs/REVIEW-v110.md` §4）。

### 3.3 全量替换而非逐条 diff

`PUT /api/policies/{id}/coverages` 收整张表，服务端 `DELETE` + `INSERT`。
前端就是一张可增删的表格，整体覆盖不会出现「删了没删掉、改了一半」的中间态。

## 4. 报告口径（报告本身的可信度全靠这一节）

### 4.1 什么算「在保」

```
in_force = status ∈ {生效中, 已缴清} 且 (无保障结束日 or 保障结束日 >= today)
```

- 已退保 / 已失效 → 不计入保障与保费合计（但仍出现在保单汇总表，标注状态）；
- 已过保障期但状态还写「生效中」→ 同样不计入，并单独列进 `expired[]` + 警示 + 行动项
  （这是最容易自欺的情况：以为是保的，其实断了）；
- `coverage_end_date` 为空 = 终身 → 永不过期。

### 4.2 保额怎么加

| 类别 | 汇总方式 | 理由 |
|---|---|---|
| 重大疾病 / 身故全残 / 意外 | **累加** | 给付型，多张保单可叠加理赔 |
| 医疗 | **取最大值** | 报销型限额，200 万 + 400 万 ≠ 600 万 |
| 年金 / 中症 / 轻症 / 豁免 | 单列，不进「给付型保额」 | 不是身故/重疾口径，混进去会虚高 |

不变式：`overview.totalSumInsured == Σ 各成员 (重疾 + 身故全残 + 意外)`。

### 4.3 多被保人保单

保额**统一记主被保人**（`policies.insured_id`）。夫妻共保的定寿，条款里各自保额通常分列，
一个字段还原不了；归主被保人 + 明确提示「请核对本人份额」，好过平分或虚高。

配套：其他被保人记 `sharedPolicyCount` + `sharedNotes`，并且**不再对该类别算缺口**
（否则会给配偶凭空造出 155 万寿险缺口——我们根本不知道他的份额）。

### 4.4 缺口公式（行业经验值，报告里必须标注「非监管标准」）

| 项目 | 参考值 | 适用 |
|---|---|---|
| 重疾 | `max(3 × 年收入, 30 万)` | 成年人 |
| 重疾 | 50 万（治疗 + 康复成本） | 未成年人 |
| 寿险 | `负债余额 + 5 × 年生活支出` | 仅本人 / 配偶 |
| 意外 | `max(5 × 年收入, 50 万)` | 成年人 |
| 意外 | 20 万（<10 岁）/ 50 万（10–17 岁） | 未成年人，按身故给付监管上限 |
| 医疗 | 只判有无 | 报销型，额度取决于就医习惯，算不准 |

未成年人不用收入倍数：孩子没有收入，按 `3 × 家庭年收入` 会得出「6 岁孩子需要 90 万重疾」
这种看似精确、实则无依据的数；意外保额还受监管上限约束，写高了没意义。

### 4.5 保费

- 按**投保人**归属（与看板一致）；
- 年化保费 = 年缴金额 / 月缴 × 12 / 趸交 0（`calc_schedule` 既有口径）；
- `premium.byMonth` 12 个月合计 **恒等于** 年化合计：月缴用 `allocate_amounts` 平摊
  （尾差归最后一个月），年缴落在生效月；
- 负担率 = 年化保费 / 家庭年收入，经验区间 5%–15%。

## 5. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/policies/{id}/coverages` | 责任明细 + 该险种模板 + 类别字典（一次请求够用） |
| PUT | `/api/policies/{id}/coverages` | 全量替换 |
| GET | `/api/report` | 现算整份报告 |
| PUT | `/api/report/params` | 保存 3 个测算参数（键缺省 = 不改，null = 清空） |
| GET | `/api/report/export.docx` | 导出 Word（与页面同源数据） |

全部挂在 `dependencies=_PROTECTED` 下（v1.9 的访问密码守卫）。

## 6. 前端

### 6.1 报告页（`static/js/views/report.js`）

九章：总览矩阵 / 缺口 / 诊断小结 / 成员逐人 / 保费分布 / 保单汇总 / 交费计划 / 行动清单 / 口径说明。

- 事件全部**委托在容器上且只绑一次**（`dataset.reportBound`）——
  每次刷新都整块替换 `innerHTML`，按渲染次数绑监听器会越刷越卡；
- 打印用原生 `@media print`：A4、每章另起一页、封面独占首页、表头跨页重复，
  不引入任何 PDF 库；
- 导出的 PDF 与页面所见一致，`Ctrl+P` 即得。

### 6.2 责任录入弹窗（`static/js/components/coverageModal.js`）

8 列表格 + 「按模板填充」（同名去重）+ 实时「给付型合计」。
合计**不乘赔付次数**：报告里的保额口径就是单次可赔金额，乘了会和报告对不上。

### 6.3 打印分页实测

演示数据（3 人 / 6 张单）导出 **11 页**：封面 1 + 九章（成员分析占 2 页）。
