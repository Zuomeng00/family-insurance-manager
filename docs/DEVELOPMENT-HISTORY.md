## 1. 起点：v1.0（2026-09-17）

### 用户原话

> 录入保单（保险公司/险种/产品名/投保人/被保人/生效日/保多久/交多久/缴费方式/每期保费），
> 按家庭成员与险种统计，展示年度总保费、近 60 天待交保费。先本地网页跑通，后期 Docker 部署。

一句话概括这个工具的存在理由：**防漏缴**。后面所有口径上的争论，最后都是拿这一条裁决的。

### 五个定调决策（改坏了就是推翻地基）

1. **不做纯前端，一步到位「后端 + SQLite」。**
   原 PRD 打算 P0 用 IndexedDB、Docker 阶段再加后端，被我推翻：那样等于 Docker 阶段重写数据层 + 迁移数据，纯返工。
   现在本地跑和 NAS 跑只差一层容器，**零迁移**。

2. **前端零构建、零 CDN。**
   原生 HTML + ES Module + 原生 CSS，由 FastAPI `StaticFiles` 托管。理由：这是要装在 NAS 上、可能要离线用的家庭工具，
   引入 Vite/React/npm 只会多一层随时会坏的东西。**这条是硬约束，至今没破。**

3. **金额在 DB 里存整数「分」。**
   `Money` TypeDecorator + 计算用 `Decimal` + `ROUND_HALF_UP`，杜绝浮点误差。
   副作用：Pydantic v2 默认把 `Decimal` 序列化成**字符串**，必须加 `@field_serializer` 转 float。
   **这个坑后来在 v1.4、v1.7 新增字段时各咬了一次。**

4. **`k_max`（当前是第几期）必须由 `due(k) < today` 反推，禁止日历算术。**
   纯日历差值公式与 `add_months` 的月末钳制不可调和：`2020-01-31` 加 1 月得 `2020-02-29`，
   按日历算会漏一期；精确周年日又会多算一期。**两处边界都实测过。**

5. **缴费日等于今天 → 计入待缴，不计为已缴**（严格小于）。
   在缴费日当天把应缴项藏起来，对这个工具来说就是功能性缺陷。

## 2. v1.1：缴费记录（同一天）

### 用户原话

> 保单录入后没办法录入已经缴费几年了，当年是否已缴费等信息。
> 工具怎么知道我今年缴费了呢？

用户自认是新手小白，给了两个方案让他选，他选「**填期数 + 单期打勾**」。

### 关键判断

- **加一个可空列 `paid_periods_override`，而不是新建一张缴费记录表。**
  `NULL` = 按生效日自动推算（保持 v1.0 行为，存量零迁移）；非 NULL = 以用户记录为准。
  逐期明细（每期具体哪天交的）留作 P2。**最小变更 + 一处真源**。
- **顺手引入「逾期」概念。** 这是手动覆盖的必然结果：用户填的已缴期数少于按时间应缴的期数，
  说明这些期次过了缴费日却没交。不单独暴露的话，**用户漏缴了反而在界面上看不见**——直接背叛工具的核心目的。
- **「已缴」按钮只出现在最早那一行。** `pay-next` 登记的是「最早未缴期次」，有逾期的保单不给按钮，
  改为提示「有逾期，请先补缴」，强制按现实顺序先补历史。
- **轻量增量迁移机制诞生。** `app/main.py` 的 `_ADDITIVE_COLUMNS` + `_run_additive_migrations`：
  `create_all` 只建缺失的表、**不给既有表加列**，所以新增列必须手动登记。这条规矩至今有效。

### 这一版留下的最贵教训

**文件编辑工具会「报成功但未落盘」，连续发生 3 次**，全靠端到端验证才发现：
`policy_service.update_policy` 赋值丢失、`calc.enumerate_upcoming` 起点没改、`policyForm.collect()` 读到值却没写进 payload。

从此定下铁律：**绝不对同一文件并行发起编辑；每次编辑后回读磁盘复核；关键逻辑必须真调接口 / 真跑浏览器。**
（v1.7 时又遇到一次类似形态的问题：`node --check` 通过 ≠ 文件没被改坏。）

## 3. v1.2：售后信息 · 批量编辑 · PDF（同一天）

### 需求来源

用户直接甩来一张某保险 App 的截图（服务顾问、保险公司电话、投保渠道、批量编辑），
并确认：PDF 是**上传挂载到保单下**（自动识别填字段可以延后）、售后信息**存在保单上 + 常用值提示**、批量编辑**需要**。

### 三个「不做」比「做」更重要

- **PDF 自动识别预填：不做。**
  真实中文电子保单的字段识别准确率不可控，而这工具是防漏缴工具——**静默填错比不填更危险**；
  扫描件、图片型 PDF 更没有 OCR 能力。架构上留了扩展点，但明确延后。
- **「选顾问姓名自动带出电话微信」：不做。** 容易张冠李戴。
- **「保险公司名称」不新增字段，复用既有 `company`。** 只加 `companyPhone`，避免双写不一致。

### 批量编辑的三态语义（最要命的设计）

| 请求体 | 含义 |
|---|---|
| 键**不存在** | 不改 |
| 键存在，**字符串**（trim 后非空） | 设为该值 |
| 键存在，**`null`** | **显式清空** |
| 键存在，**空串** | 按「不改」处理 |

前端「留空」= 不发这个键；「高级 · 设为空」= 发 `null`。
**目的就一个：杜绝「我留空表示不改，结果它给我清空了」。** QA 用 2000 组 / 139790 字段单元验过差异为 0。

### 附件安全三条红线

1. 落盘名**服务端生成** `uuid4().hex + ".pdf"`，客户端文件名**绝不参与拼路径**（防目录穿越）；
2. 用**文件头 magic bytes `%PDF`** 判定，不看 content-type、不看扩展名；
3. **流式读取、边读边累计大小**，超限立刻中止，不先读进内存。

配套两条：多文件上传 **all-or-nothing**（任一失败则回删已写文件 + 不提交任何 DB 行）；
删除顺序**先提交 DB、再 best-effort 删磁盘**（孤儿文件无害，悬挂记录有害）。

附件目录 `./data/attachments` 与 `./data/insurance.db` 同源，**Docker 只需挂一个卷**。
这一版唯一的新增依赖是 `python-multipart==0.0.20`（FastAPI `UploadFile` 必需，纯 Python）。

## 4. v1.3：一单多被保人（2026-09-18）

用户已经在极空间上部署成功了，一次提了 4 项：一张保单保多人、成员页看保障类型、新增分红险、列表直接看 PDF。

这版是**统计口径史上最危险的一版**——因为引入了「保费按人头分摊」。

### 存储

- 保留 `policies.insured_id` 作**主被保人**（NOT NULL / FK RESTRICT）；
- 新增关联表 `policy_insureds(policy_id, member_id)` **复合主键**，policy 侧 CASCADE、member 侧 RESTRICT，
  存**全部**被保人（含主被保人）= 单一真源。
- **不变式：主被保人必在关联表内。** 响应里 `insuredId == primaryInsuredId`，兼容旧调用。

### 分摊规则（刻意不一致，最容易被后人"顺手统一"改坏）

- `allocate_amounts(total, n)`：Decimal + ROUND_HALF_UP + 2 位，**尾差归最后一份**，
  不变式 `Σ == money(total)`。
- **只有 `byInsured` 的三个金额（年化 / 近60天 / 已缴）分摊**；
  `policyCount` / `activePolicyCount` **全额**；`byPolicyholder` / 顶部卡片 / `byType` **一律不分摊**。
- 排序唯一真源 `insured_sort_key = (关系序, 姓名, id)`，同时决定展示顺序、分摊顺序、**尾差归属**。
  QA 用「打乱插入顺序的 3 人保单」证伪了「按插入顺序分」。
- 单人保单 `N=1` → `allocate_amounts(total,1) == [total]` 恒等 →
  **这就是算例集 A/B/C 在 v1.3 后逐值不变的数学原因**。

### 两个我自己复核出来的点（没有只信报告）

1. **`insurance_type` 根本没有 CHECK 约束。**
   产品经理标了「新增分红险有兼容性风险」，若照做会白重建 `policies` 表、还有真实数据风险。
   我实测 SQLAlchemy 2.0.54：`Enum(native_enum=False)` 的 `create_constraint` **默认 False**，
   真实库的建表语句只有 `VARCHAR(8) NOT NULL`。→ **新增枚举值零迁移**，同时勘误了 `ARCHITECTURE.md` §3.1。
2. **迁移在真实库副本上验证**：建表 + 回填 + 主被保人在关联表内 + 连启两次幂等 + 数据无损。

### 两个「不扩大范围」的裁定

- 业务逻辑里的**条件字面量**（如 `coverageType === '终身'`）不改造——它们是规则，不是枚举副本；
- 但前端硬编码的**枚举默认值**（7 处）必须修，改由 `/api/meta/enums` 派生。
  注意 `paymentTermType` 取 **index=1**、`gender` 取 **index=2**，**不是取首项**，否则行为会变。

## 5. v1.4：看板双口径（同一天）

用户提出「年度总保费」这个数字看不懂——它把已缴清的也算进去了。于是拆成两张卡：

| 卡片 | 字段 | 条件 |
|---|---|---|
| **当年应缴总保费**（原「年度总保费」改名） | `annualTotalPremium` | Σ 年化，`status ∈ {生效中, 已缴清}` |
| **当年未缴费金额**（新增） | `unpaidAnnualPremium` | Σ 年化，`status == 生效中 且 未缴清`（= v1.3 旧口径，**逐值不变**） |

**为什么是拆而不是直接改**：只放宽主卡片会让「Σ 成员保费」对不上账（成员维度没放宽）。
拆开后各自可对账，且**旧数字一个都没变，只是换到了新卡片**。

边界要记牢：已退保 / 已失效**两个口径都不进**；趸交年化 0，两个口径贡献都是 0；
**`生效中` 但期次已缴完 → 只进「应缴」、不进「未缴」**（这正是新口径的核心差异）。

## 6. v1.5：界面优化 + 全站响应式 + 按投保人排除（09-19）

### 用户原话（两条）

> 现在总览看板五个小模块分成了两行，第二行很空。另外显示界面优化一下排版，
> 兼顾电脑浏览器显示和手机浏览器显示，都能够方便查看和编辑。

> 在保单录入里面可以手动选择是否计入总保费统计，或者让我能手工选部分投保人投保的保险才计入我的家庭保费统计。

### 「第二行很空」的根因

`.metrics` 写死了 `grid-template-columns: repeat(4, 1fr)`，5 张卡只能排成 4+1。
**5 是质数**，grid 怎么分都会留下孤行。改成 `flex + flex-wrap`，
`flex: 1 1 calc(20% - 14px)` 让最后一行自动撑满。

### 手机整页能左右拖 —— 一个典型的 CSS 隐式行为

grid 子项默认 `min-width: auto`，内嵌表格的最小内容宽度把网格撑破了。
修复只有一行：`.panel-grid > * { min-width: 0 }`。**这个 bug 从外面看像是"表格太宽"，实际是网格的锅。**

### 「计入统计」的设计

- 开关放在**成员**上（`Member.count_in_stats`，默认 True，零迁移），不是放在保单上——
  用户的原话是「哪些投保人投保的保险」。
- 过滤**只作用于「年化保费」口径**；计数、待缴、逾期、已缴一律不过滤。
- **判断依据是「该保单的投保人」，不是被保人。** 张三给李四买的保单，排除张三后，
  这笔年化要从**李四那一行**也消失。
- 收尾时我主动发现一个真问题：`/api/members` 的年化没应用排除过滤，跟看板 `byInsured` 打架。
  抽出公共函数 `insured_service.excluded_holder_ids()` 给两处共用，**禁止分叉**。

## 7. v1.6：口径放宽 + 图表改了五版（09-19）

### 问题一：一张"已缴完"的医疗险显示 ¥0

> 为什么没有显示某成员的医疗险的年化保费

v1.4 放宽了主卡片的统计方式，但三个维度（被保人 / 险种 / 投保人）**还是旧统计方式**（生效中**且未缴清**）。
1 年期医疗险交完就变 0，跟主卡片对不上账。

用 `AskUserQuestion` 给用户两个选项，他选了**「放宽」**，并确认**保单列表保持真实值**（不改展示）。
于是三个维度统一为 `status ∈ {生效中, 已缴清}`，新的对账关系变成：

> **Σ 三维度年化 == `annualTotalPremium`**（不再是 `unpaidAnnualPremium`）

**这一条推翻的是 v1.4 定下的不变式②**，`ARCHITECTURE.md` §5.5 和 MEMORY 里都要同时改，否则以后必然有人按旧不变式"修 bug"。

### 问题二：柱状图被读成"只交了一半"——改了 5 版

> 车险 2500，绿色只占一半，视觉上以为只缴费了一半。你最好把总金额和待缴比例结合起来一起显示

| 版本 | 做法 | 用户反馈 |
|---|---|---|
| ① | 灰底轨 + 已缴段填充 | 「像只缴了一半」 |
| ② | 删灰底轨 + 深色待缴段 | 「**还是**感觉只交了一半」 |
| ③ | 换饼图 | 还行，但「两边都是饼状图，视觉上没那么好看」 |
| ④ | 100% 堆叠条 | 「**不如第一种设计**」（丢掉了大小对比） |
| ⑤ | **回柱状图 + 直角条 + 刻度轴 + 网格线** | 定稿 |

**真正根因是三个线索叠加**：灰底轨、圆角胶囊（像进度条）、**没有刻度**。
前四版每次只拆一个线索，所以每次都被读成"没填完"。

定下的规则（已写进 `chart.js` 文件头）：

> **不要用柱状图表达"占比构成"。** 柱状图用长度编码数值，短的那根后面必然留白，
> 读者会把它读成"没填满 / 只缴了一半"——这是长度编码本身的歧义，改配色、去底轨都救不回来。
> 真要留柱状图，**必须有刻度轴**。

配色上也踩了一次：待缴段原本用 `#f59e0b`，几乎和医疗险的 `#f59f00` 撞色。
改成**同色加深**（本条色叠 `#000` opacity .34 + 2px 白线），从此不依赖调色板剩余色。
**教训：配色不要靠肉眼估，要抓实际渲染出来的 `fill` 与 `DEFAULT_COLORS` 比对。**

## 8. v1.7：真实待缴 + 首页筛选（09-20）

### 用户原话

> 面板首页的「当年未缴费金额」，是指的生效中且未缴清保单的年化保费合计；这个可以保留，
> 换个名字比如「年化保费合计」，增加一个统计口径「当年未缴费金额」，
> 我想知道的是真正当年没有缴费待缴的金额。
> 还有个需求，我想能够首页手工筛选，哪些投保人、哪些险种不计入年度保费统计。

### ① 「当年未缴费金额」到底是年化还是真实待缴

老卡片叫「当年未缴费金额」但装的是**年化**（把未来几年的保费摊平到一年），
用户要的是**真金白银今年要掏多少**。两件事差很远。

- 老卡片**只改名**：`unpaidAnnualPremium` → 展示名「年化保费合计」，数字一个不动。
- 新卡片：`OverviewOut.year_unpaid_premium` = **本年度到期且未标记已缴**的期次金额合计。
  用新函数 `calc.enumerate_year_periods()` 枚举 `due(k).year == 本年度` 且 `k >= paid_periods` 的期次。
- **含已逾期**、含本年度尚未到期的期次；金额用 `premium_per_period`（**不是年化**）。
- 经用户确认的两个选择：**含逆期**、**两种口径都要**。

**这张新卡不受筛选影响**，这是我审过的关键判断：
现金流就是现金流，排掉某个投保人不等于这钱不用交了。如果让它跟着筛选走，
用户会误以为今年只需交这么多 → **直接造成漏缴**，跟工具的存在目的冲突。

### ② 首页筛选：临时筛选 vs 存为默认

- 维度：**投保人 + 险种**，两者是**并集排除**（任一命中即排除）。
- 临时勾选**不落库、不发请求**，纯前端重算，刷新即重置；点「存为默认」才落库。
  用户要的是"我临时看看"，不是"每点一下都改配置"。
- 投保人沿用 `Member.count_in_stats`（**零迁移**）；险种新增表
  `stats_exclusions(kind, ref_id)` 复合主键，由 `create_all` 自动建（**新表不需要登记 `_ADDITIVE_COLUMNS`**）。
- 接口 `GET` / `PUT /api/stats/exclusions`，PUT 是**全量替换**；非法值 422，**不新增错误码**。
- 成员表单里那个「计入家庭保费统计」开关**移除了**，合并到首页统一管；成员列表改成只读的「统计状态」列。

### ③ 卡片 5 张变 6 张

6 能被 3 和 2 整除 → 任何视口都不会出现孤行。桌面 3×2 / ≤1100px 2×3 / ≤640px 2×3。

### ④ 一个被堵住的高危陷阱（值得记住的思考方式）

`MemberUpdate.count_in_stats` 默认值是 `True`。前端编辑成员时如果**省略**这个字段，
Pydantic 会把它填成 `True` → 一个已经被排除的成员被**静默重置为"计入"**，
用户看到的年度保费莫名其妙变大，而且**没有任何提示**。

当前靠 `members.js` 提交时回填现值兜住，QA 做了端到端验证。
**更彻底的修法是 `Optional[bool] = None`（省略 = 不修改）**，这是遗留待办 #1。

这类 bug 的形态值得记：**默认值 + 部分更新 = 静默覆盖**。凡是 PATCH/PUT 用的 schema，默认值都要警惕。

## 9. v1.8：企业微信到期提醒（11-09）

### 9.1 需求原话

> 「帮我增加一个消息通知功能，可以保险快到期了自动提醒我。通过企业微信机器人通知」
> 「发你的图片是其他软件的功能，供你参考」

配图是别的保单管理 App 的提醒设置页（启用开关 + 「提前 N 天」+ 「提醒时间」）。**语义参考，不照抄版式。**

### 9.2 第一层判断：提醒的"触发点"到底是什么

图里只有一句「提前 N 天」，但本工具里**有两个"到期"**，而且业务含义完全不同：

| 到期对象 | 语义 | 用户要做什么 | 数据来源 |
|---|---|---|---|
| **保障到期** `coverage_end_date` | 这份保险快保不住了 | 续保 / 换产品 | v1.8 **新增**的派生字段 |
| **缴费到期** `next_due_date` | 这一期该交钱了 | 交钱（或标记已缴） | v1.1 就有 |

**只做一个是不够的**：只做保障到期，会漏掉"长期险要交 20 年"这类每年都得交的钱；
只做缴费到期，会漏掉"一年期意外险该续保了"。所以**两类都做，各自独立开关与天数**。

### 9.3 关键设计决定

**① 新增 `Schedule.coverage_end_date`，而不是在通知服务里自己算**

`calc.py` 是项目里"日期口径"的唯一真源（月末钳制、2/29 回退、生效日在未来这些坑都在这）。
通知服务若自己 `add_years(effective_date, term)` 重算一遍，两处口径迟早分叉。
所以把「保障结束日」做成 `Schedule` 的字段、经 `PolicyOut.coverageEndDate` 透出，
前端以后要用也直接取——**一次算对，两处用**。

**② 一条汇总消息，不是逐单推送**

一天收七八条「XX 保单要到期了」会让人直接把这个机器人静音。改为一条消息分两段、
应缴段带合计金额；单类超 20 条折叠为「另有 N 条未列出」（企业微信 markdown 有长度上限，宁可折叠不要截断）。

**③ 去重靠日期字符串，不靠内存状态**

`notify.last_sent_date` 存 `"2026-11-09"`。**进程重启不会重发**，也不需要任何定时器状态机。
只用一个 `while True + sleep(60)` 轮询，判断「`now >= send_time` 且 `last_sent_date != today`」——
比 cron 表达式、APScheduler 简单得多，也不新增依赖。

**④ 补发语义（想清楚才敢这么做）**

09:00 该发，但服务 11:00 才起来 → **当天仍然会发一条**。因为漏发的代价（错过续保）远大于晚发的代价。
反过来，如果 09:00 就起来了、发过一条，之后重启多少次都不会再发第二条。

**⑤ 通知失败不能拖垮应用（红线）**

`run_check_safe()` 吞掉**所有**异常只记 WARNING；`_notification_loop()` 再兜一层。
NAS 上网络抖一下、企业微信接口 502，最坏结果是"今天没收到提醒"，绝不能是"工具打不开了"。

**⑥ Webhook 脱敏 + 拒收脱敏值**

最初的实现里，`GET` 返回 `key=****1234`，前端保存时把整个表单 PUT 回来——
**这把真实 key 覆盖成了星号**，而且不会报错，下次发送就 401。发现得早（写测试时想到），
在 `validate_webhook()` 里加了 `"****" in url → 422`。**脱敏数据永远不能回流成写入值。**

**⑦ 只用标准库 `urllib`**

一个 POST JSON 的请求，引入 requests / httpx 会让镜像依赖层变化（约 +1MB，且要重新校验 wheel）。
标准库够用，代价是要自己写 `HTTPError / URLError / JSONDecodeError` 三种分支——
顺手把常见 `errcode` 翻译成人话（`93000` → 「Webhook 地址无效或机器人已被移除」）。

### 9.4 配置存哪：新表 or 加列

| 方案 | 结论 |
|---|---|
| 在 `members` / `policies` 上加列 | ❌ 通知配置与应用级、与具体实体无关 |
| 复用 `stats_exclusions` 那种专用表 | ❌ 每加一个配置项就要改表结构 |
| **`app_settings(key, value)` 键值表** | ✅ **缺键即取默认值**，存量库零迁移、零回填，以后加配置只加一行 |

`AppSetting.__repr__` 故意不打印 `value`——`logger.debug(policy)` 这类顺手调试最容易把 key 带进日志。

### 9.5 版本号与镜像

`1.8.1`。`docker-compose.yml` 的 `image:` 同步升到 `1.8.1`——
**这条必须与镜像一起发**，否则用户粘了新 compose 却拉到不存在的 tag，容器起不来。

### 9.6 上线一小时后被打回：微信里看不到

阿白装好、配上、收到了消息——**在电脑上的企业微信里**。转头用手机微信打开同一个群，
只看到两行「**暂不支持此消息类型，点击前往企业微信查看**」。

**根因**：群开了「微信互通」时，微信端只渲染 `text` 与 `image`。
`markdown`（我首发用的类型）、`news`、`file`、`voice`、`template_card` 一律降级成那句提示。
官方原话：「微信内不支持展示 Markdown、图文、文件等消息类型，仅支持文本和图片。」

**改法**：`msgtype` 换成 `text`，消息结构重写：

| 原来（markdown） | 现在（text） |
|---|---|
| `## 标题` / `### 小节` | `家庭保单提醒（日期）` + `【保障即将到期】共 N 份` |
| `> 引用块` | `· 条目` + 两空格缩进的第二行 |
| `<font color="warning">已逾期 3 天</font>` | 纯文字「已逾期 3 天」（靠字词强调，不靠颜色） |
| 上限 4096 字节 | 上限 **2048 字节** → `MAX_BYTES=2000` 按字节预算折叠 |

**判据也补了**：测试里断言 `"##" / "> " / "<font" / "**"` 一个都不许出现——
这类"看起来更漂亮"的标记，恰恰是让消息在微信里消失的原因。

### 9.7 顺带修掉的「重复推送」

他截图里是**两条一模一样**的消息。原因是我自己埋的：

- 他在 13:32 才第一次打开开关，而发送时间是 09:00 → `now >= send_time` 且 `last_sent_date` 为空
  → 我那套「补发」逻辑**立刻**推了一条；
- 他刚点了「立即发送测试」，又收到一条。

**补发**这个设计本身没错（服务整个上午没起，下午起来该补），但它分不清
「服务宕了」和「用户刚打开」。改法：**由关到开的那一次**，若当前时间已过发送时间，
就把 `last_sent_date` 记为今天——今天不补，从明天起正常。
发送时间还没到就开启的，不写标记，当天照发。

> 教训：**"补发"是给已存在状态用的，不能无差别套在"首次启用"上。**

## 10. v1.9：访问密码（11-10）

### 10.1 需求原话

> 「增加一个访问密码功能，版本号小变动就行。」

一句话需求，没有任何细节。这类需求最容易做歪——**做重了**（用户要的只是「别人打开时别直接看到」），
**做轻了**（加了密码却忘了留后门，最后把用户自己关在门外）。

### 10.2 第一层判断：三道必须先答的问题

| 问题 | 决定 | 理由 |
|---|---|---|
| 默认开还是关？ | **关** | 升级即自动开启 = 用户打开网址被一句「请输入密码」堵住，而他根本不知道有这回事。默认关，谁要谁开 |
| 忘了密码怎么办？ | **必须留后门** | 单用户工具、密码全家共用一个。没有后门 = 一次忘记就重装。给了两条：环境变量 `AUTH_DISABLED` + 直接改库 |
| 密码存哪？ | **只存哈希，Cookie 存签名** | 库里存明文等于没加锁；Cookie 存 token 且 HttpOnly，JS 摸不到 |

### 10.3 被推翻的方案

**① 「用一个 `password` 字段 + 前端校验」**
最开始有人（我）想的是最省事的：设置页把密码存进 `app_settings`，前端进入前比对一下。
**这是假锁**——所有 `/api/*` 照样裸奔，随便一个 `curl` 就全拿到了。加锁必须加在**服务端**。

**② 用中间件拦所有请求**
看着最"全局"，实际有两个硬伤：

- 拿不到 `Depends(get_db)`，只能自己开 `SessionLocal` → 测试里（内存库 + 依赖覆盖）
  会读**另一个数据库**，守卫静默失效；
- 放行名单要按路径字符串手工维护（`/api/health`、`/api/auth/*`、静态资源…），
  以后加接口时容易漏。

改成挂在 `include_router(..., dependencies=[Depends(require_auth)])` 上：与业务路由共用同一个会话，
且**新路由默认不带守卫**——加业务时被迫想一下「这个要不要保护」，而不是默认裸奔。

**③ 会话表 / Redis / JWT 库**
都不必要。token = `HMAC(secret, "过期时间.密码版本")`，**无状态**：
不建表、不加依赖、服务重启不掉线。改密码时「密码版本」跟着变，旧 token 自动全废——
这正好也是「改了密码，其它设备应该掉线」这个语义，一个机制满足两个需求。

### 10.4 四个实现细节（都是踩出来的）

**① 登录响应不能复用「读请求 Cookie」来算状态**
`login()` 里先 `set_cookie` 再调 `_current(request)` —— 读到的还是**请求带来的旧 Cookie**，
于是返回 `authenticated:false`，前端刚登录成功又被弹回登录页。
必须用**刚签发的那串 token** 去算状态。

**② Cookie 不能加 `Secure`**
加了就只在 https 下发送。家用 NAS 大多是 `http://192.168.x.x:8000`，
表现为「密码明明是对的，进去了又让你登」，极难排查。用 `HttpOnly + SameSite=Lax` 就够：
JS 读不到（防 XSS 偷 token），Lax 保证附件 `<a href>` 跳转能带上。

**③ 401 广播要排除登录接口自己**
前端统一在 `request()` 里 `401 → 广播 app:unauthorized → 弹登录页`。
但密码输错也是 401 —— 一次输错就把登录页重渲染，**输入框清空、错误提示也一起被冲掉**，
用户看到的是「点了没反应」。所以 `path === '/auth/login'` 时**不广播**。

**④ 闸门可见时不要再渲染视图**
登录过期后闸门弹出来，若此时还有 `app:refresh` 触发 `route()`，视图会在遮罩后面继续发请求 →
继续 401 → 继续弹闸门 → 又清空一次输入。加一行 `if (isLoginGateVisible()) return;` 就安静了。

### 10.5 限速：只锁 IP，5 分钟 5 次

账号只有一个、密码全家共用，不限速等于把暴力破解的窗口开到无限大。
锁定期间**即使密码正确也返回 429**——否则限速只是「多试几次」而已。

进程内实现（`dict[ip] -> [时间戳]` + `threading.Lock`）：家用单实例部署够用，
重启即清零；不为此引入 Redis。

### 10.6 测试怎么写的

35 例，重点不在 happy path，而在**「锁是不是真的锁上了」**：

- 9 个业务端点逐个断言未登录返回 401 —— 防的是「以后新增接口忘了挂守卫」；
- 建 Cookie 的三个属性（`HttpOnly` / `SameSite=Lax` / **无** `Secure`）都断言了；
- 改密码后拿**旧 token** 访问必须 401；
- 手工签一个**已过期但签名正确**的 token → 401（证明兜底靠有效期，不是靠签名错）；
- 把库里 `auth.secret` 换掉 → 401（模拟恢复旧备份）；
- 库内任何配置值都不许出现明文密码；
- 把 PBKDF2 迭代数从 1000 调大后，旧哈希仍能校验通过（证明「按存储的迭代数重算」）。

最后一条顺带解决了测试速度：`_check_hash` 从存储里读迭代数，测试把常量调到 1000 就快，且不影响正确性。

### 10.7 数据迁移：零

密码 / 开关 / 密钥都进 `app_settings`（v1.8 建的表），**缺键即默认值**。
不新增表、不新增列、不登记 `_ADDITIVE_COLUMNS`、不回填。升级就是换个镜像。

## 12. 交付链路是怎么演进的

本机**从头到尾没装 Docker**。所以镜像不是 `docker build` 出来的，是用 Python 直接拼 OCI 布局：

```
step1_pull_base.py   拉官方 python:3.13-slim 的 config + 4 个层，校验每层解压后 SHA256 == 官方 diff_ids
step2_*              装依赖（manylinux x86_64 预编译 wheel，逐条记录 diff_id）
step3_assemble.py    组装镜像 → dist/family-insurance-manager-X.Y.Z-amd64.tar
step4_verify.py      结构校验（85 项：层摘要、逐层叠加文件系统、控制台脚本 shebang、import 完整性…）
step5_final_audit.py 内容审计（21 项：应用层与仓库源文件逐字节一致、LABEL、RepoTags…）
```

**合计 106 项校验，必须 106 PASS / 0 FAIL。**

两个每次都要看的信号：

- **依赖层 diff_id**：从 v1.2 到 v1.7 一直是 `c95070ea3454341b`。**变了 = 引入了新依赖**，得确认是不是有意的。
- **应用层 diff_id**：不变说明打包没吃到改动。

踩过的坑：moby v27 的 `save` 已改成 OCI 布局（`blobs/sha256/*` + `index.json` + `oci-layout`），
早期脚本按老格式解析直接失败；后来因为元数据缺 `os/architecture` 又重打过一次（**层内容没变，只改元数据**）。

**部署侧的硬规矩**：`docker-compose.yml` 的 `image:` 标签必须跟版本号同步，
否则 NAS 上拉起的还是旧镜像——这是最容易漏、也最难看出来的一处。

## 13. 踩坑史（按类别，都是真踩过的）

### 12.1 工程环境

| 坑 | 症状 | 对策 |
|---|---|---|
| 编辑报成功但未落盘 | 工具返回 success，磁盘没变 | 绝不并行编辑同一文件；每次编辑后回读磁盘 |
| `node --check` 漏报 | 注释块被切坏、留下野文本，语法检查仍通过 | 语法通过 ≠ 文件没改坏，必须回读上下文 |
| MSYS `/tmp` 与 Windows `/tmp` 不是一处 | 文件"写了读不到" | 临时文件一律用系统临时目录（`%TEMP%`）的绝对路径 |
| stdout 采集间歇失效 | 连 `echo` 都返回空，其实命令在跑 | 输出重定向到文件 + Read 回读 |
| CDP `Runtime.evaluate` 取值层级 | `Received undefined` | 正确是 `ev.result.result.value` |

### 12.2 业务与统计

| 坑 | 教训 |
|---|---|
| 测试写死用户活数据规模（`policyTotal == 3`） | 用户加一张保单测试就红。**从库里 `SELECT COUNT(*)` 读出来再比** |
| 跨页面数字打架（`/api/members` 与看板） | 同一口径必须抽公共函数，**禁止两处各算一遍** |
| 手抄种子数据当硬基准 | 我按记忆手算算例 A 的期望值，差点判定架构师算错，结果**是我错了**。**硬基准必须回源核对** |
| 默认值 + 部分更新 = 静默覆盖 | 见 v1.7 §8④ |
| 新表在测试里不存在 | 测试只调 `build_dashboard()` 没走应用启动路径，`create_all` 没执行。**别为此删用例**，这些用例守的是"真实库不被改动"的红线 |

### 12.3 视觉与图表

| 坑 | 教训 |
|---|---|
| 柱状图被读成进度条 | 长度编码 + 无刻度 = 必然被误读。**占比用饼图/堆叠条**，柱状图**必须带刻度轴** |
| 待缴段与调色板撞色 | 配色不靠肉眼估，抓实际渲染的 `fill` 比对 |
| 5 张卡 4+1 孤行 | 用 flex-wrap 而不是固定列数 |
| 手机整页横滚 | grid 子项 `min-width: 0` |

## 15. 下次迭代时怎么用这份记录

1. **先看第 10 节那张口径表**，确认你要改的指标现在归哪个视角（统计 / 分摊 / 现金流）。
